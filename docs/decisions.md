# Decisions

Every product or design decision taken while building SnapFlow 2, newest step last. "Claude" decisions were made during implementation on a stated reason; overrule any of them and the next step changes the code. Open questions carry the assumption the code follows until they are answered.

## Decided

| # | Step | Decision | Reason | By |
| --- | --- | --- | --- | --- |
| D1 | 1a | Opaque server-side sessions (hashed token in Postgres, HttpOnly SameSite=Lax cookie; bearer accepted for API/MCP) instead of JWT + refresh tokens | Deactivation and role changes apply at once; cookies also authenticate image and file requests | Claude |
| D2 | 1a | Three fixed, ordered roles (admin > tenant_admin > user); the permission matrix lives in code (`platform/auth`), shown read-only on the Roles page | Explicit, testable matrix; custom roles are not needed yet | Claude |
| D3 | 1a | Permission checks run in the services, not in HTTP middleware | MCP (phase 4) calls the services and must inherit every check | Claude |
| D4 | 1a | Exactly one distributor tenant, created at startup, cannot be deactivated or deleted; admins must belong to it | Matches how SnapFlow is run; SnapFlow 1 allowed several distributors by accident | Claude |
| D5 | 1a | Nobody assigns or changes a role above their own; nobody changes their own role, tenant or active flag, deletes themselves, or sets their own password through user management | Closes SnapFlow 1's admin-takeover bug and prevents lock-outs | Claude |
| D6 | 1a | The last active admin cannot be demoted, deactivated or deleted (checked under a row lock) | Concurrent edits could otherwise leave no admin | Claude |
| D7 | 1a | Login limits count failed attempts per email and client IP (plus looser per-email and per-IP caps); `TRUSTED_PROXIES` decides which X-Forwarded-For entries are trusted | A per-email-only limit let anyone lock out any account | Claude |
| D8 | 1a | A correct password on a disabled account returns "account disabled" (as in SnapFlow 1) | Users need to know to contact their admin; it reveals only that the password is right | Claude |
| D9 | 1a | Passwords: argon2id, at least 8 characters everywhere; emails case-insensitive; a password change ends all other sessions; "sign out everywhere" exists | SnapFlow 1 had three different minimum lengths and no revocation | Claude |
| D10 | 1a | First admin from `ADMIN_EMAIL` / `ADMIN_PASSWORD` when no active admin exists; an existing user with that email is promoted | No hard-coded or logged passwords | Claude |
| D11 | 1a | The Roles page is visible to every logged-in user | The API allows it and users should see what their role may do | Claude |
| D12 | 1a | Postgres row-level security arrives in phase 2 with projects; until then tenant isolation is enforced in the services | Users are the only tenant-owned data so far | Claude |
| D13 | 2 | Deleting a partner tenant that has projects is a soft delete: the tenant is deactivated and archived, its projects and users are kept. Tenants without projects are hard-deleted (with their users) | Keeps project history | User |
| D14 | 1b | SnapFlow 1 categories and item types merge into product types; the old item type (e.g. Zigbee) becomes an attribute such as `bus_system` | The rewrite plan's migration table maps categories and item types to product types | Claude |
| D15 | 1b | Product types define two attribute schemas now (product/variant attributes and per-instance attributes); the channel template follows in phase 3 with distribution boards | Instance data is part of the plan's data model; channels are only needed by the board editor | Claude |
| D16 | 1b | Product types are edited on a page, not in a dialog | Attribute schemas are too long for a dialog | Claude |
| D17 | 1b | The catalog is global and maintained only by distributor admins (`catalog.write`); tenants cannot add their own products | Follows D4: the distributor runs SnapFlow and owns the catalog; same as SnapFlow 1 | Claude |
| D18 | 1c | One global list price per variant; tenant-specific pricing (markups, discounts) comes later as a tenant setting, not as catalog data | Follows D17: one catalog, one price list; discounts already live on the proposal | Claude |
| D19 | 1c | Catalog base currency is USD; projects store their own currency and exchange rate (architecture.md) | SnapFlow 1 prices are USD, so migrated prices and BOM snapshots stay exact | Claude |
| D20 | 1b | Metric only; attribute units are display text without conversion | The board designer's feet display is the only imperial use and can be a view option later | Claude |
| D21 | 1a | End-to-end tests with Playwright in Chromium (from Nix, version-pinned to nixpkgs' playwright-driver), against a production build of the frontend, its own backend and a database recreated on every run (`make e2e`, CI job `e2e`) | Same browsers locally and in CI without downloads; the dev database can never be touched; no dev-server reloads mid-test | Claude |
| D22 | 1b | Saving a schema drops the fields that do not apply to an attribute's type (options of a text attribute, min/max of a boolean, item type of a non-list) instead of rejecting them; product attributes without a scope get "product". Lengths and item counts are whole numbers from 0, integer bounds are whole | The editor can keep hidden inputs when the type changes, and stored schemas stay clean | Claude |
| D23 | 1b | Attribute values: blank text, blank enum and empty lists count as "not set"; a list of enum options is a set (repeats collapse); text length counts characters; keys of the other scope are rejected (`attribute.wrong_scope`), unknown keys as in D31 | One rule for the editor, the import (1d) and instances; typos in imports must not be stored silently | Claude |
| D24 | 1b | Every validation problem of a product type (key, name, every attribute row, both schemas) is reported in one response, each at its exact location (e.g. `body.attributes[2].options[0].key`) | Long schemas would otherwise need one save per mistake | Claude |
| D25 | 1b | The catalog order is one order over active and inactive product types; reordering sends the complete list | Reactivating a type puts it back where it was; a complete list detects concurrent changes (`product_type.order_mismatch`) | Claude |
| D26 | 1b | Product type schema changes are always allowed. Products are re-validated against the current schema when they are saved (1c), and the product list will flag products whose values no longer match (was Q1) | Follows the "extend with data, not code" principle (D15): changing a schema must not need a data migration | Claude |
| D27 | 1b | Users without `catalog.write` open the same product type editor page read-only (every control disabled, no save, a "Back to list" link); the name in the list links there. `catalog/product-types/new` needs `catalog.write` | One page to build and test instead of a separate detail view; readers still see the full schema | Claude |
| D28 | 1b | Saving the product type editor returns to the list. Leaving the editor with unsaved changes (Cancel, a link, back) asks first ("Discard unsaved changes?": Leave page / Stay, the data router's `useBlocker`), and closing or reloading the tab triggers the browser's `beforeunload` prompt; without changes nothing is asked | Long schemas are a lot of work to lose to a stray click; the prompt only appears when there is something to lose, so the plain flow stays the same as the dialogs (save closes, cancel leaves) | Claude |
| D29 | 1b | Reordering on the list moves a type past its visible neighbour; with inactive types hidden, the move is applied to the full order (fetched fresh) and the complete id list is sent | Follows D24; hidden inactive types keep their relative place | Claude |
| D30 | 1b | Integer values and integer bounds (also lengths and item counts) are limited to ±(2^53−1); beyond that values fail with `attribute.range`, bounds with `attribute.bound_range` | Every integer stays exact as float64, in jsonb read-backs and in JavaScript; values read back from jsonb are re-normalised by `ValidateValues` | Claude |
| D31 | 1b | Stale values: product saves (1c) keep values whose key is no longer in the schema, untouched and without an error (`ValidateValues` with `Unknown: Keep` returns them separately); reads flag them and the product editor offers to remove them. Imports use `Unknown: Reject` and report them as `attribute.unknown` | Renaming or removing an attribute must not block saving a product or silently delete data; imports must not store typos | Claude |
| D32 | 1d | The import gets a lenient cell parser that feeds `ValidateValues`: decimal comma, yes/no/ja/nein/1/0 for booleans, enum options by key or label (case-insensitive), lists split from one cell, blank items dropped. Not built in 1b | Spreadsheets hold text in local formats; `ValidateValues` stays the one strict rule | Claude |
| D33 | 1b | Request fields with a fixed set of values (attribute type, item type, scope) are validated by the API schema (OpenAPI enum); a wrong value comes back as `validation.invalid` at its location before the service validates anything else, so other problems of that save show only after it is fixed. An empty string is a wrong value too | The editor only offers valid values, so this only affects other API clients, and the allowed values stay visible in the OpenAPI document | Claude |
| D34 | 1b | Schemas that no value can satisfy are rejected: a required text or list with a maximum below 1 (`attribute.required_max`), a list of options whose minimum is above the number of options (`attribute.min_above_options`) | Such an attribute would make every product of the type unsaveable | Claude |
| D35 | 1b | Lists bound only their item count; per-item bounds (`itemMin`/`itemMax`) come when a real attribute needs them (e.g. channel currents in phase 3) | No current attribute needs them; adding optional fields later needs no migration | Claude |
| D36 | 1b | Translatable texts accept only the known locales (en, de; `i18n.Locales`, which must match the frontend's language list), others fail with `validation.locale`. Lengths: product type name 100 characters, description 2000, attribute and option labels 100, attribute descriptions 500 (`validation.too_long` with `max`). Applies to function types too | Text under an unknown locale would be stored but never shown; bounded texts keep lists and exports readable | Claude |
| D37 | 1b | Optimistic concurrency for long editors: an update sends `expectedUpdatedAt` (the `updatedAt` it was edited from) and fails with 409 `<entity>.stale` if the record changed since, checked in the UPDATE itself. Product types first; every long editor from now on follows this pattern | Two admins editing the same schema would otherwise overwrite each other's work without noticing | Claude |
| D38 | 1b | Product types have an optional colour (`#rrggbb`, stored lower case) shown as a badge in lists and the configurator palette; it replaces SnapFlow 1's item type colour badge, the item type abbreviation is dropped | The badge helps users find types in long lists; the abbreviation duplicated the name | Claude |
| D39 | 1b | Field errors carry params, and a code is only used when its params are always present: value ranges are `attribute.range` (min and max), `attribute.range_min` or `attribute.range_max`, likewise `attribute.length*` for text and `attribute.count*` for list items. Schema bounds: `attribute.bound_whole`, `attribute.bound_negative`, `attribute.bound_range` (min, max) and `attribute.range_invalid` (min above max, param min). Too-long integer bounds use `attribute.bound_range`, not `attribute.range_invalid` | Every translated message can name its limits without placeholders that might be empty | Claude |
| D40 | 1b | Schemas hold at most 200 attributes and 500 options per attribute, checked in the service (`validation.too_many` with `max`) rather than by OpenAPI `maxItems` | The framework's error has no specific code, so the editor could not explain it | Claude |
| D41 | 2 | SnapFlow 1's per-project product type filter of the configurator palette moves to phase 2: projects choose their product types | Projects do not exist before phase 2 | Claude |
| D42 | 1c | SnapFlow 1's category deactivation cascade is replaced by computed availability: a variant is available only when the variant, its product and its product type are active. Nothing cascades, so reactivating a type restores exactly what was available before | A cascade loses which items were deactivated on their own | Claude |
| D43 | 1b | Anonymous catalog reads are gone: every catalog read needs a login (architecture principle "every read and file needs login") | SnapFlow 1 served categories, items, variants, add-ons and uploads without login (inventory 01, catalog import); the catalog is the distributor's data | Claude |
| D44 | 1b | The product type editor never starts from cached data: it fetches the type on every visit (`staleTime: 0`, `refetchOnMount: 'always'`) and shows "Loading" until that fetch is done. The form edits that loaded version; background refetches never change it or its `expectedUpdatedAt`. On `product_type.stale` the message offers "Reload", which restarts the form from the current version and discards the edits (the message says to make them again) | With D37 no one overwrites a newer version unknowingly, and no one starts editing an old one; a merge view is not worth it for an admin-only page | Claude |
| D45 | 1b | Long schemas in the editor: attribute cards collapse (collapsed when an existing type is opened, open in create mode and for new rows; read-only users see every card open, since the disabled form would disable the toggles) and show "Label · type · unit · required · scope" when collapsed; "Expand all / Collapse all"; per card move up/down, to top/bottom, insert below, duplicate and remove. "Add attribute" appears above the list (adds at the top) and below it (adds at the end). A duplicate copies everything and its key gets `_copy`, which must be changed before saving (`attribute.key_copy`, checked only in the editor) | Schemas with dozens of attributes stay navigable; an unchanged copy key would silently create a near-duplicate attribute | Claude |
| D46 | 1b | Field errors after a save: each API location is shown at a field only if the editor renders that field for the row's current type (otherwise the message above the buttons spells it out, never "check the highlighted fields" without a highlight); list-wide errors (`validation.too_many`, `attribute.options_required`) show next to the list; `product_type.key_taken` (409 without location) also marks the Key field. Rows with errors open and are marked in their header, and focus moves to the first error in page order | Every error is visible where it can be fixed, also in a collapsed card; keyboard and screen reader users land on it | Claude |
| D47 | 1b | Form error messages carry their params ("validation.too_long" with `max`): the frontend keeps a typed list of which error keys need which params (checked against errors.json by a test), so a key whose text has placeholders cannot be used without them, in zod schemas or from the API | Messages name their limits (D39) on the client too; a forgotten param would show an empty placeholder | Claude |
| D48 | 1b | Attribute bounds are text inputs (`inputMode` numeric for lengths and item counts, decimal otherwise) so that invalid input reaches validation (`validation.number`); the editor mirrors the server's bound checks with its codes (`attribute.bound_whole`, `bound_negative`, `bound_range`, `range_invalid`, `required_max`) and the text limits of D36/D40 | A number input reports invalid text as empty, which would silently drop a bound; mirroring saves a round trip, the server stays the authority | Claude |
| D49 | 1b | The product type list shows each row's position among the rows shown (1..n) instead of the stored sort order, and the name with its colour as a dot (`TypeBadge`, also for 1c's product list and pickers). The colour is picked with the browser's colour picker or typed as hex (`ColorField`), without presets. A reorder whose visible neighbour (or the moved type) is missing from the freshly fetched full list sends nothing and shows `product_type.order_mismatch`; deleting a type also drops its cached detail | Sort orders count hidden inactive types and would show gaps; a move against a list that changed meanwhile could land anywhere | Claude |
| D50 | 1c | A product is one orderable device model of a product type: model number (the business key, trimmed, at most 100 characters, unique ignoring case across the whole catalog), translatable name (200 characters, `en` required, not unique) and description (5000), product-scope attribute values and an active flag. The product type reference is `ON DELETE RESTRICT`, which makes `product_type.in_use` real. SnapFlow 1's fixed `dimensions` column becomes an attribute of the type | SnapFlow 1 was unique in the UI but per type in the sync, which duplicated products; the rewrite plan turns fixed columns into attributes | Claude |
| D51 | 1c | A variant (SnapFlow 1 "style") is a sellable version of a product: translatable name (100 characters, `en` required, unique per product ignoring case on `en`; "Standard" when a product has one variant), optional SKU (100, unique ignoring case when set; the import will fill it with "Model Number + Style"), price, optional image, variant-scope values, a position and an active flag. A product may have no variants; the UI encourages one | The style name is how SnapFlow 1 and its workbook identify variants; SKUs are what ERP and orders need later | Claude |
| D52 | 1c | Money in the API is a decimal string with two places (`"27.00"`), accepted as `^\d{1,10}(\.\d{1,2})?$` (so no `.5`, `1.234`, `-1`, `1e3` or 11 integer digits: `variant.price_format`); `numeric(12,2)` (≥ 0) in Postgres; a string in Go, compared with `math/big`. A JSON number is refused by the API schema | Floats cannot hold cents exactly; one strict format avoids locale ambiguity (the import's lenient parser, D32, converts before it) | Claude |
| D53 | 1c | An add-on links a variant to another variant with `required` (default false: SnapFlow 1's UI default; its API default true was a bug) and a position; a pair exists once; a variant cannot be its own add-on; cycles are allowed (as in SnapFlow 1). The editor replaces a variant's complete add-on list in one request (`{addons: [{addonVariantId, required}]}`, order = list order, at most 100), all problems reported together at `body.addons[i].addonVariantId` | One explicit save per variant instead of SnapFlow 1's immediate add/remove calls; a full list makes the order and concurrent edits simple. The body is an object (not a bare array) like `{ids}` of the reorders, so fields can be added | Claude |
| D54 | 1c | Availability as in D42: the API returns each own `isActive` and a computed `available` (variant ∧ product ∧ type; product ∧ type on products and list rows). The default product list shows only available products, `includeInactive=true` all of them; the variant search lists every variant with its `available` flag | The editor must show both why something is unavailable and what its own flag is; the add-on picker may link inactive variants (the BOM in phase 2 adds only available required add-ons) | Claude |
| D55 | 1c | Stale values on products and variants (D31 applied): reads return `attributes` (keys the schema has, as stored), `staleAttributes` and `attributeErrors` (problems of the stored values against the current schema, at `attributes.<key>`, with params); list rows count both over the product and its variants. A save keeps a stale key only if it was stored before and is sent back, and then keeps the stored value untouched; leaving it out removes it; a key never stored is `attribute.unknown`. Changing a product's type re-validates the same way. A key whose attribute moved to the other scope is an error (`attribute.wrong_scope`, D23), not stale | The editor sends the stale values back unchanged to keep them and drops one for "Remove", so no extra API is needed; clients cannot store arbitrary new keys or alter stale data they cannot see validated | Claude |
| D56 | 1c | Product and variant updates are optimistic (D37: `expectedUpdatedAt`, 409 `product.stale` / `variant.stale`). Replacing add-ons and reordering variants change neither updatedAt nor need it: the add-on list is replaced whole under a row lock, reorders send the exact set (`variant.order_mismatch`) | Saving the add-ons must not make the open variant form stale; both operations already detect or serialise concurrent changes | Claude |
| D57 | 1c | Product rows, the product detail and variant search results carry the product type (`productType`: id, key, name, colour, active) for the type badge (D38, D49) | Lists and pickers show the badge without a second request | Claude |
| D58 | 1c | Images live in a `files` feature: metadata table (id, sha256 unique, content type, size, width, height) and content-addressed storage on disk under `STORAGE_DIR` (default `./data/files`, sharded `ab/cd/<sha256>`, written via temp file and rename). Uploads (`catalog.write` for now) accept JPEG, PNG and WebP by magic bytes only (415 `file.type`), at most 10 MB (413 `file.too_large`) and 40 megapixels (422 `file.too_many_pixels`); JPEG and PNG must decode completely, are turned upright by their EXIF orientation and scaled down to 1600 px wide in the same format (JPEG quality 85, PNG with transparency); WebP is stored as uploaded. The same stored bytes give the same file. Downloads need a login and are `private, immutable` with the SHA-256 as ETag and `nosniff`. Unreferenced files are kept until a cleanup job exists (not in 1c) | SnapFlow 1 served all uploads publicly and overwrote shared Excel image names; content addressing makes files immutable and cacheable; re-encoding drops EXIF, so orientation must be applied or phone photos turn sideways | Claude |
| D59 | 1c | Deleting a product hard-deletes it with its variants and their add-on links in both directions; deleting a variant removes its links both ways; images stay (D58). BOM lines (phase 2) keep their snapshot and a nullable reference | SnapFlow 1 behaviour without its file deletions, which broke images other variants still used | Claude |
| D60 | 1c | Products read product type facts (catalog order, active flags, schemas) through `producttypes.Service` and pass them to their queries as arrays (`unnest(type_ids) WITH ORDINALITY`, `inactive_type_ids`) instead of joining `product_types`; file ids are checked through `files.Service` (and foreign keys) | CLAUDE.md rule 3: features do not read each other's tables. There are few product types, so the extra call is cheap | Claude |
| D61 | 1c | The product list: `limit` 1–200 (default 50) and `offset` ≥ 0 are validated (422), never capped; `search` is trimmed and matched case-insensitively as a substring with `%`, `_` and `\` literal, over model number, English and German name and the variants' SKUs (the variant search also over variant names); order: product type order, model number ignoring case, id. Rows carry the variant count (all variants) and the price range and preview image (first by variant order with an image) of the variants whose own flag is active | SnapFlow 1 capped silently (its pickers lost items beyond 100) and treated `%`/`_` as wildcards. The spec's "first available variant" equals "first active variant" for available products, since product and type flags are the same for all of a product's variants; using the own flag also keeps a preview and price range for inactive products in the admin list | Claude |
| D62 | 1c | `STORAGE_DIR` is a new setting (default `./data/files`, i.e. `backend/data/files` in development, ignored by git; `/data/files` on the `app-files` volume in Docker). Backend tests use a temporary directory per test, the end-to-end backend a temporary directory emptied on start | Files must never land in the repository or survive between test runs | Claude |
