# Architecture

Decisions as of 2026-10-18. The full plan with diagrams lives in the "SnapFlow 2 – Rewrite Plan" document; this file is the in-repo summary and wins if they differ.

## Goals

The top priority is that new features, importers and exporters are easy to add in backend and frontend without breaking unrelated code. SnapFlow 1 failed here because logic was duplicated (invoice maths existed five times and the copies disagreed), the schema was rigid, and the UI bypassed its own components.

## Principles

1. Every business rule exists once, in the backend.
2. Layers: HTTP (`api.go`) → service (rules) → generated store (SQL). The domain knows no HTTP.
3. The API contract is generated from Go code (OpenAPI); the TypeScript client is generated from that. An API change breaks the frontend build, not production.
4. Extend with data, not code: product attributes and function types are configuration; plan kinds, bus systems, importers and exporters are modules behind interfaces.
5. Geometry and interaction run in the editor for live feedback; the backend validates the saved state and returns BOM and warnings.
6. Strict design system, enforced by a test.
7. Tenant isolation checked in code and by Postgres row-level security.
8. i18n from day one: UI, catalog content and exports. The API returns error codes, the client translates them. Server errors (5xx) never carry error text: the cause is logged with the request id and the response has a fixed detail (`platform/apperr`).

## Domain model

- **Global catalog** (shared by all tenants): function types (dimmer, switching, blind, …), product types (systems and product lines such as Zigbee or KNX, shown as a badge), categories (kinds of device) with an attribute schema, a channel template and an instance schema, products (each of one product type and one category) with variants and addons (attribute values as validated jsonb, translatable names).
- **Projects** (per tenant) with versions. A project has any number of **plans**: floorplans (image, zones, placements) and distribution boards (enclosure, rails, module instances), not tied to a floor.
- **Zones hold loads** ("ceiling light living room", dimmer, 60 W). **Channel assignment** wires each load to exactly one module channel on any board.
- **Project BOM** = BOM lines of all plans + manual lines; each line keeps a frozen snapshot and a catalog reference ("Update from catalog").
- **Checks**: bus load (current used vs. supplied, per bus system and board), channel balance, warnings.
- **Bus system adapters** (HDL first, KNX later): assign addresses, validate, export a config file for the vendor tool. Direct programming via a local bridge agent may come later.
- **Revisions**: proposal, as-built and programmed states as snapshots.
- Customers stay embedded in projects for now.

## Auth, tenants and permissions

- **Tenants**: exactly one *distributor* tenant (runs SnapFlow, owns the catalog, home of the admins; created at startup, cannot be deactivated or deleted) and any number of *partner* tenants. Deleting a partner deletes its users; what happens to a tenant that has projects is decided in phase 2.
- **Roles** are fixed and ordered: `admin` > `tenant_admin` > `user`. Nobody assigns a role above their own or changes a user whose role is above their own. Nobody changes their own role, tenant, active flag or password (via user management; the profile is the place for that), or deletes themselves. At least one active admin always remains (`user.last_admin`): user updates and deletes run in one transaction that locks the active admin rows (in id order, then the target row) whenever an active admin would lose that status, so concurrent changes cannot remove the last one. `admin` requires the distributor tenant. On startup, if there is no active admin, `ADMIN_EMAIL`/`ADMIN_PASSWORD` creates one, or promotes the existing user with that email (moved to the distributor, activated, password reset, sessions ended, logged); without `ADMIN_EMAIL` a warning is logged.
- **Permission matrix** in `backend/internal/platform/auth` (pinned by `TestMatrix`): `catalog.read` (all), `catalog.write` (admin), `projects.read`/`write` (all), `projects.delete` (admin, tenant_admin), `users.manage` (admin, tenant_admin), `tenants.manage` and `tenants.access_all` (admin). `GET /api/roles` returns it; the Roles page shows it.
- **Where checks run**: every service operation starts with `auth.Require(ctx, permission)`, so the HTTP API and the MCP server share them. The HTTP middleware only authenticates and refuses anonymous calls to non-public operations (`auth.Public` marks the exceptions). Tenant scoping uses `actor.SeesTenant`; rows of other tenants look like 404.
- **The UI never re-implements rules**: `/api/auth/me` returns the user's permissions and assignable roles, and rows carry `can.update`/`can.delete`. The frontend gates pages, navigation and buttons with `useCan()` and those flags.
- **Sessions**: opaque random tokens; only their SHA-256 is stored. The browser gets an HttpOnly, SameSite=Lax cookie; `Authorization: Bearer` with the same token is accepted for API clients (MCP later). Sessions expire 14 days after last use (renewed at most hourly, which re-sends the cookie). User, role, tenant and active flags are read on every request, so changes apply at once. Changing a password ends the user's other sessions; an admin resetting someone's password ends all of theirs. `POST /api/auth/logout` ends the current session; `POST /api/auth/logout-all` ("sign out everywhere") ends all of the caller's sessions, the current one included. Passwords: argon2id, at least 8 characters, at most one hash per CPU at a time (a request that waits more than 5 s for a slot gets 503 `server.busy`); emails are case-insensitive.
- **CSRF**: every non-safe request that a browser marks as cross-site (`Sec-Fetch-Site` other than `same-origin`/`none`) is refused, whatever the credentials (cookie, bearer or none, e.g. login). Non-browser clients send no `Sec-Fetch-Site` and are unaffected.
- **Login limiting** (in memory, one instance): only *failed* logins count, so a stranger cannot lock an account's owner out. Limits per 5 minutes: 10 failures per (email, client IP), 50 per email (distributed guessing), 100 per client IP (password spraying). A successful login clears its (email, client IP) bucket. Wrong current passwords on the password change are limited to 10 per user. Every 429 `auth.too_many_attempts` carries `params.seconds` and a `Retry-After` header.
- **Client IP**: the connection's address, unless it comes from a proxy listed in `TRUSTED_PROXIES` (comma-separated CIDRs or addresses); then the rightmost `X-Forwarded-For` entry that is not itself a trusted proxy. Without trusted proxies `X-Forwarded-For` is ignored, as anyone could set it. Determined by HTTP middleware (`platform/clientip`) and passed to the service as an argument.
- **Disabled accounts**: with the *right* password, a disabled user (or a user of a disabled tenant) gets 403 `auth.account_disabled`, so they know to contact their admin (as in v1, deliberately). With a wrong password the answer is the usual `auth.invalid_credentials`, so the flag does not leak without the password.
- **Row-level security** arrives in phase 2 with projects, the first tenant-owned business data. Until then tenant isolation is enforced in the services.

## Catalog: product types, categories and attribute schemas

The catalog has two independent axes (D99, replacing D14): the **product type** is the system or product line a device belongs to, the **category** the kind of device whose attributes it has. Every product has one of each.

- **Product types** (`features/producttypes`) are the systems and product lines ("Zigbee", "KNX", "HDL Buspro"). Each has a key (lower snake case, 1–64 characters, unique), a translatable name (100 characters), an optional abbreviation (badge text such as "ZB": trimmed, upper case, at most 6 characters, D101) and an optional colour (`#rrggbb`, D38), a position in one global catalog order (`PUT /api/product-types/order` with every id, D25) and an active flag (inactive types are hidden from lists unless `includeInactive=true`). They have no schema. Lists, selects and the add-on picker show them as a badge: the abbreviation on the colour, or a dot (`TypeBadge`, D103). Projects choose their product types (phase 2); the configurator palette shows only those, grouped by category (D41). A type that products use cannot be deleted (`product_type.in_use`, 409).
- **Categories** (`features/categories`) are the kinds of device ("Gateways", "Touchscreens", "Dimmer actuators"): key, translatable name (100 characters) and description (2000), a position in their own catalog order (`PUT /api/categories/order`), an active flag and two attribute schemas stored as jsonb: `attributes` (values on the product, or per variant with `scope: "variant"`) and `instanceAttributes` (per installed unit, used from phase 2/3; their definitions have no scope). The channel template follows in phase 3. A category that products use cannot be deleted (`category.in_use`, 409); deactivate it instead. Errors use `category.*` codes (`key_format`, `key_taken`, `not_found`, `order_mismatch`, `stale`, `in_use`).
- **Migration** (D100): `00007_categories` turned every former product type (which carried the schema) into a category with the same id and data, set each product's category to it and removed the schema from `product_types`; the product types kept their old names until an admin renames them to systems.
- **Concurrency** (both): creates and reorders run in a transaction holding one advisory lock per table (`pg_advisory_xact_lock`), so sort orders never collide; a reorder also row-locks every row, so none is deleted underneath it. Updates are optimistic (D37): the body carries `expectedUpdatedAt`, the UPDATE matches it, and a mismatch is 409 `product_type.stale` / `category.stale`.
- **Attribute schemas** (`platform/attrschema`, pure Go) are configuration, never migrations. A definition has a key, label (100 characters), optional description (500) and unit (display only, D20), a type (`text`, `number`, `integer`, `boolean`, `enum`, `list` of `text`/`number`/`integer`/`enum`), `required`, optional `min`/`max` (value range; length for text; item count for lists, D35) and `options` for enums. At most 200 attributes and 500 options (D40); integers within ±(2^53−1) (D30); schemas no value can satisfy are rejected (D34). `CheckSchema`/`CheckInstanceSchema` check and normalise a schema when it is saved (D22); `ValidateValues`/`ValidateInstanceValues` check and normalise the values of a product, variant or unit against it (D23) and are the one implementation products (1c), the import (1d, behind a lenient cell parser, D32) and instances use. With `Unknown: Keep` (product saves) values of keys the schema no longer has come back as stale instead of failing (D31); `Unknown: Reject` (imports) reports them.
- **Translatable texts** (`i18n.Text`) accept only `i18n.Locales` (en, de; the frontend's `contentLocales` must match) and `en` is required (D36). Forms edit each in one `TranslatableField` with a tab per language of that list (D109), so a new language needs no form changes.
- **Errors**: all problems of a save come back in one 422 with per-field codes (`attribute.*`, `category.*`, `product_type.*`, `validation.*`) and params (e.g. `max`, `min`, `options`, `expected`, `scope`) at exact locations such as `body.attributes[2].options[0].key`, so the editor shows each next to its row (D24, D39). Fields with a fixed set of values (type, item type, scope) are checked by the API schema first (D33).
- **Editors** (`frontend/src/features/categories`, `frontend/src/features/product-types`): categories have one page per category for create, edit and read-only view (D27) with the schema; product types are edited in a dialog with a badge preview (D102). The category page always loads the current version and sends it back as `expectedUpdatedAt` (D37, D44), asks before unsaved changes are lost (D28), keeps long schemas navigable with collapsible attribute cards (D45) and shows every server error at its field or spelled out (D46, D47).

## Catalog: products, variants, add-ons and files

- **Products** (`features/products`, one aggregate with variants and add-ons) are orderable device models: a product type and a category (both required, FK `RESTRICT`, which makes `product_type.in_use` and `category.in_use` real; a new product needs active ones, `product.type_inactive` / `product.category_inactive`, D78), a **model number** (the business key, trimmed, at most 100 characters, unique ignoring case across the whole catalog: `product.model_number_taken` with `modelNumber`), a translatable name (200, `en` required, not unique) and description (5000), product-scope attribute values (jsonb) and an active flag. SnapFlow 1's fixed `dimensions` column becomes an attribute of the category (D50).
- **Variants** (SnapFlow 1 "styles") are the sellable versions: a translatable name (100, `en` required, unique per product ignoring case on `en`: `variant.name_taken`), an optional SKU (100, unique ignoring case: `variant.sku_taken`), a **price**, an optional image (file id), variant-scope values, a position within the product (`PUT /api/products/{id}/variants/order` with every id: `variant.order_mismatch`) and an active flag (D51).
- **Money** is a decimal string with two places in the API (`"27.00"`, accepted as `^\d{1,10}(\.\d{1,2})?$`, else `variant.price_format`), `numeric(12,2)` in Postgres and a string in Go (compared with `math/big`), never a float. Prices are list prices in USD (D19, D52).
- **Add-ons** link a variant to other variants (any product, cycles allowed) with `required` (default false; required add-ons are added to the BOM automatically in phase 2). The whole list is replaced at once (`PUT …/variants/{variantId}/addons`, `{addons: [{addonVariantId, required}]}`, order = list order, at most 100) in one transaction that shares the product (`FOR KEY SHARE`), then locks the variant (`FOR NO KEY UPDATE`) and the add-on variants (`FOR KEY SHARE`, in id order), so concurrent replaces neither duplicate links nor wait for each other; self, duplicate and unknown entries are reported together (`addon.self`, `addon.duplicate`, `addon.variant_not_found`) (D53).
- **Availability is computed**: a variant is `available` when it, its product, the product type and the category are active; the API returns each own flag and `available`. Nothing cascades, so reactivating a type, category or product restores exactly what was available before (D42, D54). The default product list shows only available products; `includeInactive=true` shows all.
- **Schema changes** (D26, D31): reads return `attributes` (values of keys the schema has), `staleAttributes` (keys it no longer has) and `attributeErrors` (problems of the stored values against the current schema, at `attributes.<key>` with params); the list returns both as counts over the product and its variants. A save validates against the current schema with `ValidateValues(Unknown: Keep)`; a stale key is kept, with its stored value untouched, when it is sent back, removed when it is left out, and a key that was never stored is `attribute.unknown`. Values follow the category's schema. Changing a product's category validates the product's own values the same way; the variants' values are only flagged, never re-validated or refused, and the product reports `variantsWithProblems` (D55, D68, D104); changing only the product type touches no values. A new product needs an active type and category; an existing one keeps its own (D78). Model numbers and SKUs are stored in Unicode NFC and refuse control characters (`validation.control_chars`, D77).
- **Concurrency**: product and variant updates carry `expectedUpdatedAt` (409 `product.stale` / `variant.stale`, D37, D56); variant creates and reorders lock the product row so sort orders never collide; uniqueness is enforced by unique indexes (concurrent duplicates get the 409, not a 500). Lock order is the product row, then its variants (reorders lock them `FOR NO KEY UPDATE`, which does not wait for add-on `KEY SHARE` locks). Deletes cascade in their own order, so deadlocks with add-on replaces stay possible: every transaction (`database.InTx`, all features) is retried up to 3 times on a deadlock or serialization failure, then answered with 409 `request.conflict_retry` (D75). List pages read their rows and total in one read-only REPEATABLE READ transaction.
- **Lists**: `GET /api/products` (filters `productTypeId`, `categoryId`, `search`, `includeInactive`; `limit` 1–200, default 50, and `offset` validated with 422, never capped) is sorted by product type order, then category order, then model number; rows carry the type (`productType` with abbreviation and colour for the badge) and the category (`category`), variant count, price range and preview image of the active variants, and the attribute problem counts. `GET /api/variants` lists variants across the catalog for the add-on picker in catalog order (product type, category, model number, variant order): all of them without `search` (browsing, paged with `offset`), optionally of one `productTypeId` and/or `categoryId` (D83, D105). Search is a case-insensitive substring match over model number, names and descriptions (en/de) and SKUs in which `%`, `_` and `\` are literal (D61, D81). Product type facts (order, active flag, badge) come from `producttypes.Service` and category facts (order, active flag, schema) from `categories.Service`; this feature never reads `product_types` or `categories` (D60).
- **Files** (`features/files`): uploads (`POST /api/files`, multipart `file`, `catalog.write` for now) are JPEG, PNG or WebP by magic bytes (`file.type`, 415), at most 10 MB (`file.too_large`, 413, also for chunked bodies) and 25 megapixels (`file.too_many_pixels`); every image is decoded completely. JPEG and PNG are always re-encoded in their format with 8 bits per channel (no EXIF/GPS or other metadata survives), scaled down to 1600 px wide and then turned upright by their EXIF orientation; WebP is stored as uploaded (no Go encoder, so its metadata stays). Decodes share a 300 MB memory budget (`files.DecodeBudget`, D76). Limits differ from SnapFlow 1's 5 MB / 1200 px on purpose (D80). Contents live on disk under `STORAGE_DIR` (default `./data/files`), content-addressed by SHA-256 (`ab/cd/abcd…`), so the same bytes are stored once and get the same file id. `GET /api/files/{id}` needs a login (the cookie works for `<img>`) and sends `ETag` (the SHA-256), `Cache-Control: private, max-age=31536000, immutable` and `X-Content-Type-Options: nosniff`. Unreferenced files are kept until a cleanup job exists (D58). Writes are durable (file and directories fsynced); contents missing on disk are logged as an integrity error and answered with a plain 500. Files have no owner yet: any logged-in user reads any file, which a tenant scope must change before the first tenant-owned upload (D79). Other features check file ids through `files.Service.Exists`.
- **Delete** hard-deletes a product with its variants and their add-on links (both directions); deleting a variant removes its links both ways; images stay (D59).
- **Frontend** (`frontend/src/features/products`): the product list (`catalog/products`, filters for type and category in the URL, paged, D70, D105), the product page (`catalog/products/new`, `:id`: basics, attribute values, the variants below, D64, D74) and the variant page (`:id/variants/new`, `:id/variants/:variantId`: basics, image, variant attributes, add-ons with their own save, D63, D72). All page editors (categories too) follow one pattern: fresh load, `expectedUpdatedAt` with Reload, create continues on the new item's page, update stays with "Saved.", "Back to list" while clean and "Cancel" with the unsaved-changes prompt while dirty (D84). The list's filters travel in the navigation state, so leaving an editor returns to them (D86). Attribute values are edited with the shared inputs of `frontend/src/catalog` (D65–D68, D85), which the import (1d) and instances reuse; the rules stay in `attrschema`. Number and price inputs accept a decimal comma through one `parseDecimal` (D71).

## Catalog import

- **Pipeline** (D119): source adapter (`platform/importsrc`) → mapping profile → preview (diff with row errors and warnings, stored) → apply in one transaction → change log with undo (`features/imports`). Everything needs `catalog.write`. The import never touches catalog tables: it reads the catalog with `products.Service.Catalog` (every product with variants and add-ons, three queries) and writes through the products, categories and files services, so every product rule applies (product types are only read: the import never creates them).
- **Sources**: a `Source` reads a file into a `Table`: sheets, rows with their sheet row numbers, cells as text by **absolute column** (A = 0, whatever the used range), and the pictures anchored to each row. XLSX (cells with excelize, numbers cleaned to what the General format shows; pictures from the sheet's drawing part, two-cell anchors before one-cell anchors, then document order) and CSV (UTF-8 with or without BOM, `;` or `,` by the first line, quotes). Limits (D124): 50 MB (`import.too_large`, 413), 20 000 non-blank rows (`import.too_many_rows`), 5 000 pictures (`import.too_many_images`), `.xlsx` must be a ZIP and `.csv` UTF-8 text (`import.file_type`, 415; `.xls` is refused), unpacked size capped.
- **Profiles** (`import_profiles`, D120): name (unique ignoring case) and a mapping: sheet, header row, first data row, the product type (system) and the category each as a fixed id (`productTypeId`, `categoryId`) or a mapped field, "create missing categories" (`createMissingCategories`), "all or nothing" (default on) and fields. A field feeds a target from a column (header text matched ignoring case and repeated white space, else the column letter) or a constant. Targets: `product.modelNumber` (required), `product.name.<locale>`, `product.description.<locale>`, `product.productType` (key, English name or abbreviation; never created, unknown values are `import.product_type_unknown`), `product.category` (key or English name; unknown ones are `import.category_unknown` or created), `variant.name.<locale>`, `variant.sku`, `variant.price`, `variant.image`, `addon.required` / `addon.optional` (repeatable, in mapping order) and `attribute.<key>` (scope from the row's category); `GET /api/import-targets` (`categoryId` narrows it) lists them with the attribute definitions per category. Updates are optimistic (`import_profile.stale`). With no profile at all, listing creates the starter profile "SnapFlow 1 workbook" (D121: categories from Category, product type `zigbee`, which must exist).
- **Rows** (D122): one row is one variant; rows with the same model number (NFC, white space collapsed, ignoring case; `products.MatchKey`) form one product, matched across the whole catalog; the first row supplies the product fields, other values on later rows are warnings. A variant matches by English name, then by SKU within its product; an empty variant name is "Standard". Mapped fields replace the stored values (a blank cell clears an optional one), unmapped fields and stale attribute values are kept. Values go through `attrschema.ParseCell` (D32, D131) and the products service's `NormalizeProduct` / `NormalizeVariant` against the row's category, whose errors land at the row and column; unknown attribute keys are errors (D31). Changes compare normalised values, so the same file twice changes nothing.
- **Scope** (D123): products of the file's pairs of product type and category (or the fixed pair) that the file does not list are deactivated, as are the variants of imported products that it does not list; nothing is deleted, other systems and other categories are never touched, rows with errors still count as listed. Created categories (D133) get a text attribute per mapped attribute key.
- **Add-ons and pictures** (D127, D128): add-on references resolve against the file's variants, then the catalog, by SKU or "model number + variant name" (MatchKey); unresolved ones are warnings; the file's list replaces the variant's list. A row's picture (in the mapped column, or any) becomes the variant image, else the first picture of the product's rows, else the image stays; pictures are stored as files during the preview (content-addressed, so re-imports reuse them).
- **Runs** (`import_runs`, D125, D126): `POST /api/imports` (multipart `file`, optional `profileId`) stores the file through the files feature and creates a run (`uploaded`); `GET …/source` shows the columns and first rows for mapping; `POST …/preview` (`profileId` or an unsaved `mapping`) stores the diff (`import_items`: categories to create, products with their product type and category, variants with field-level before/after; `GET …/items`), the row issues (`GET …/issues`), the counts and a catalog token over product types, categories, products, variants and add-ons (`previewed`, repeatable until applied). `POST …/apply` runs the stored plan in one REPEATABLE READ transaction under an advisory lock, the services joining it through `WithTx` (each write a savepoint): `import.stale` (409) if the catalog token changed, `import.has_errors` (422) with all or nothing while rows have errors; without it rows with errors are skipped and a failing product is rolled back to its savepoint and reported. A failing write under all or nothing rolls everything back and the run is `failed` with its error. `POST …/undo` reverts an `applied` run (`undone`) from the change log (`import_changes`, `GET …/changes`) unless something it touched changed since (`import.undo_conflict` with the entities, D129).
- **Frontend** (`frontend/src/features/imports`, D135–D140): the runs list, `catalog/imports/new` (file and optional profile) and one page per run whose step follows its state: mapping (columns of the file with grouped targets, product type and category, constants, profiles), preview (counters, issues, paged diff with before/after, All or nothing, Apply) and result (change log, Undo with the conflicting entities linked).

## Extension points

| Extension | Contract |
| --- | --- |
| Feature | Vertical slice; `make feature` scaffolds it |
| Plan kind | `Validate`, `BOMLines`, `Supplies`, `Demands`, `Checks` + an editor module on a shared canvas base (react-konva) |
| Bus system | `AssignAddresses`, `Validate`, `ExportConfig` (later `Program`) |
| Import source | `importsrc.Source` reads a file into a `Table` (XLSX and CSV now, supplier APIs later) → saved mapping profile → preview with per-row errors → apply in one transaction, undoable |
| Exporter | Canonical document model → output (DOCX first; Excel, PDF, other systems later); registered in the backend, listed by the API |
| Integration | External references on every entity, scheduled jobs, outbox for reliable delivery and webhooks, per-tenant encrypted settings. ERP scope: items only, no ERP yet |
| MCP | On top of the same services, inherits every permission check |

## Decisions taken from the SnapFlow 1 inventory

All 16 recommendations were accepted, including: smart sizing (resize all instances, toggle); discount and services as percent or absolute, computed once in the backend; catalog base currency plus project currency and rate stored on the project; invoice settings per version; BOM grouped by product + variant + snapshot price; "Update from catalog" with a diff preview; read-only by project status plus permission; an explicit permission matrix; tenant admins cannot change higher roles; every read and file needs login; area assignment recomputed on change; Excel sync preview with per-row errors; missing items deactivated, not deleted; per-type documents split discount and services; undo/redo and visible save errors; versions kept with a correct deep copy. Details: `docs/inventory/`.
